Have you debugged a run that looked fine—but was not?

Training failures are hardest when nothing crashes: the run completes, but the model still behaves incorrectly.

The cause may be hidden in data handling, normalization, masking, state, artifacts, or evaluation.

01

How TrainingDxBench works

Why training diagnosis matters

Existing benchmarks target coding bugs, but subtler training bugs matter just as much.

Recursive self-improvement (RSI) requires Agents to do more than write runnable code. They must build correct, efficient training pipelines and verify that training behaves as intended.

What is a training defect?

A training defect lets the run finish, but it harms the training process or result.

A valid study compares the same workflow with and without the defect. The evidence should reveal the real cause, but finding it should still require meaningful investigation.

Training paradigms are not restricted. We welcome defects from pretraining, full-parameter supervised fine-tuning (SFT), LoRA and other parameter-efficient fine-tuning, reinforcement learning (RL), vision-language model (VLM) training, and other training workflows.

We categorize each defect by where its impact appears:

Defect observed in the training process

Changes to data exposure, supervision, loss, gradients, updates, state, artifacts, inference, scoring, or selection.

Defect observed in the training outcome

Changes in model behavior, task performance, deployment capability, or the reported conclusion.

Benchmark workflow

In each task, an Agent inspects a completed run and diagnoses the hidden defect. A Judge then evaluates the diagnosis and repair.

  1. 01 Evidence

    Observe a completed run

    Review the source, frozen inputs, logs, artifacts, checkpoints, traces, and evaluations.

  2. 02 Diagnosis

    Diagnose the hidden defect

    Form hypotheses, run focused experiments, and trace the failure to its causal mechanism.

  3. 03 Evaluation

    Judge the diagnosis and repair

    A tool-free Judge compares the Agent's explanation and repaired files with the canonical reference.

04

Evaluation framework

A private Bubblewrap sandbox gives the Agent the flawed completed workspace, GPUs, and offline experiment tools. The corrected arm and canonical reference remain hidden.

Bubblewrap-isolated flawed workspace

Investigate freely inside a bounded, offline environment

For 1,800 seconds the Agent can inspect source, data, checkpoints, traces, logs, and evaluations; edit the workspace; and run focused training, inference, gradient, or artifact experiments to test its hypotheses.

1,800s wall-clock no step or turn cap
Layer 0 Contributor phase

Agent diagnosis and submission

The Agent returns a defect explanation, repair description, modified paths, and the final edited files. The controller freezes this structured submission against a hidden flawed baseline.

→
Layer 1 Contributor phase

Tool-free semantic Judge

The Judge compares diagnosis, paths, and submitted files with the Oracle and corrected evidence, then returns independent defect_match and repair_match decisions.

→
Layer 2 After merge

Project-side repair recovery

Deferred during contribution. After merge, project reviewers can apply a semantically different repair, retrain it, and check whether the declared process and outcome metrics recover.

Contributors run Layers 0 and 1 only. Layer 2 is intentionally project-owned to keep task contribution affordable while preserving a path to causal repair verification.

05

Submission requirements

Evidence

Show process and outcome differences

Every task must document a reproducible process difference and outcome difference.

Canonical diff

Match the canonical paths

The paths listed in the Oracle must exactly match all source and data changes between the flawed and corrected workspaces.

Verifier

Recompute references

score.py must reproduce every metric declared in contract.json.

Budget

Fixed Agent time budget

Agents receive one 1,800-second wall-clock budget, with no limits on steps, turns, subruns, or updates.

Decision

Binary evaluation result

A task passes only when both the diagnosis and repair semantically match the canonical reference.

Resources

Bounded compute

Every official task must be reproducible on no more than two NVIDIA RTX A6000 GPUs.

Submission threshold One qualifying failed Agent result is sufficient to open a PR. Testing more supported models is encouraged when access and compute permit.
One-subscription Judge rule

To keep contribution accessible, use the strongest model in the same family as Judge—Claude Opus 5 for Claude Agents or GPT-5.6 Sol for GPT-5.6 Agents—at max effort, preferably through the same coding-agent runtime.

What does the diagnosis Agent receive?

Only an anonymized, independent copy of the completed flawed workspace. The Agent cannot access Task.md, the corrected workspace, Oracle, scorer, parent repository, or run metadata.

What happens when the 1,800-second budget expires?

Workspace and shell access end. The same Agent invocation returns its best final assessment, and the result records budget_exhausted: true. Running out of time does not, by itself, determine whether the repair resolves the task.

Does the final evaluation rerun the Agent's repair?

Not during contribution. Archived paired scoring establishes task validity, and an independent Judge compares the diagnosis and repair with the canonical reference. After a task is merged, the project team can add a human-reviewed Layer 2: apply a semantically different repair to a fresh flawed workspace, retrain it, and check whether the declared process and outcome metrics recover.

Can I author on different hardware?

Yes. You may use different authoring hardware, but the task must remain reproducible within the official two RTX A6000 ceiling while preserving effective batch, update budget, and mechanism semantics.
